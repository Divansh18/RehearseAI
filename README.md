# RehearseAI

RehearseAI is becoming a candidate interview platform. Signed-in candidates can attend the existing four-question Pipecat voice interview at `/interview`, then open their own saved conversation. An active account explicitly promoted to admin can review all interviews and download transcript PDFs. Scheduling is **not implemented**. The earlier take-home [recording](https://www.loom.com/share/928bba7d68ec4174856488a0ed2e1bb7), [evidence](evidence/recorded-session/), and [checklist](SUBMISSION_CHECKLIST.md) describe the prototype, not this persistent account flow.

## Pre-interview media setup

From the dashboard, open the interview room. Before any voice session starts, the page explains data use and asks you to select **Enable camera and microphone**, **Share screen**, and **Test speaker**. Confirm that you heard the test tone. Begin is enabled only while the microphone track is live, both local video previews have a current frame, and the speaker check is confirmed. A silent microphone is still considered available. The microphone stream is reused by SmallWebRTC; camera and screen tracks stay in the browser and are neither sent to the voice pipeline nor recorded or analysed. The screen request asks for video only, without system audio. This is a local device check, not identity verification or independent server proof of media activity.

The browser needs [camera/microphone permission](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) and [screen capture support](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia) in a secure context. Use `http://127.0.0.1:7860` locally or HTTPS outside localhost. Current desktop Chrome, Edge, and Firefox are the primary targets; screen capture varies across browsers and mobile devices. When `getDisplayMedia` is absent, setup explains the limitation and Begin remains disabled. The screen picker opens only from a Share screen click and must be selected again after sharing stops.

After Begin, the room keeps the same local camera stream in a mirrored self-view beside the RehearseAI identity panel. Only the camera pixels are flipped; the shared-screen preview is not. The live transcript is collapsed by default and scrolls within a bounded panel when opened. Preparing, Speaking, Listening, Paused, and Ended labels follow actual client/server lifecycle events; the speaking bars animate only after server output starts. A local preview or status label does not prove browser audio playback.

If a required track ends during an interview, an overlay stays in the room, identifies the lost requirement, and cancels pending coach audio through the Pipecat interruption path. The server drops partial candidate transcription while paused; the controller keeps the question, memory, and probe allowance. Restore the device with the overlay controls, then click **Resume interview**; End interview remains available. If a candidate turn was active at loss, Resume waits for Pipecat's existing turn-stop boundary before accepting another answer; wait for the Listening status. No second silence timer is used. A loss during connection setup blocks the greeting until media is restored and Resume is clicked. End interview, logout, navigation, completion, and unrecoverable connection failure release camera, microphone, screen, meter, and preview resources. Browser lifecycle cleanup is best effort on abrupt tab/process closure. The existing server-output delivery acknowledgment remains an approximation of playback.

Manual media check: sign in, open `/interview`, verify Begin is disabled, deny one device and confirm the error, then enable camera/mic, share a screen, test and confirm the speaker, and click Begin once. Confirm the greeting begins only then. Stop screen sharing while the coach is speaking; check that speech stops and no question advances. Restore sharing, click Resume, and answer the pending question. Repeat with microphone loss and then End while paused. Confirm tracks stop on End, logout, and navigation. These steps require a real browser and devices; automated media tests use synthetic tracks.

## Run locally

Python **3.11+**, [uv](https://docs.astral.sh/uv/getting-started/installation/), and Docker Compose are required for local development. Start persistent PostgreSQL and a local Mailpit inbox:

```sh
docker compose up -d --wait
uv sync --frozen --group dev
test -f .env || cp .env.example .env
```

If `.env` already exists, keep it and add the new account variables from `.env.example` rather than overwriting it. Set `REHEARSE_AUTH_SECRET` to a locally generated value of at least 32 characters (`python -c 'import secrets; print(secrets.token_urlsafe(48))'`). The local `DATABASE_URL` in `.env.example` points to the Compose development database. The test database is separate. Fill in server-side `DEEPGRAM_API_KEY`, `OPENAI_API_KEY`, and `CARTESIA_API_KEY` from [Deepgram](https://developers.deepgram.com/docs/create-additional-api-keys), [OpenAI](https://platform.openai.com/api-keys), and [Cartesia](https://play.cartesia.ai/keys). Cartesia is not needed if `REHEARSE_TTS_PROVIDER=openai`. Keys never belong in browser assets.

Apply the explicit migration, then start the app:

```sh
uv run alembic upgrade head
uv run python -m rehearse_ai
```

Open **http://127.0.0.1:7860/**. Create an account, then sign in immediately with its email and password. Registration does not send a verification email or confirm email ownership. `/dashboard` is protected. Each accepted voice connection creates a saved attempt tied to the server-authenticated account. The dashboard shows its real records; there are no scheduled appointments or example interviews. To designate an admin, create an active account, then run:

Anonymous visits to `/` go to the sign-in page, which links to registration and password reset. The interview page links back to the dashboard and offers logout; expired sessions return to sign-in with an explanation before microphone setup. The browser sends the signed CSRF token alongside the authenticated WebRTC offer.

```sh
uv run python -m rehearse_ai.admin admin@example.com
```

Replace the email with that active account's address. No admin account is created automatically. Sign in normally and open `/admin/interviews`. Candidates can view only their own ordered conversations; only admins can download or regenerate private PDFs. `docker compose down` stops local services without deleting the database volume; do not use `down -v` unless you deliberately want to remove local data. The app binds to loopback.

## Saved interviews and PDFs

Migration `0003_interview_records` adds `interview_record` and `interview_transcript`. A successful WebRTC setup creates a `starting` record; opening `/interview` alone creates none. The existing `session_started` event changes it to `in_progress`. Only `interview_complete`, emitted after the controller's normal closing delivery event, marks it `completed`; `interview_ended_early` marks it `ended_early`. A disconnect before either marks it `interrupted`; an unexpected pipeline worker failure marks it `failed`. Restart reconciliation marks abandoned `starting`/`in_progress` attempts `interrupted` with reason `server_restart`. Terminal states are latched against late callbacks. The record stores its account ID, UTC timestamps where known, status/reason, source build ID, and prompt hash. No appointment or scheduling row exists.

The server's raw JSONL remains the ordered source event trail. A bounded 1,024-event queue writes candidate final STT and assistant prepared text incrementally to PostgreSQL. Candidate turns use the Pipecat turn-boundary frame ID for duplicate detection when available; older events fall back to a turn number or event sequence. Assistant utterances use their ID. Assistant status moves through prepared, output started, and server output completed; cancellation, interruption, and failure remain distinct. A generated-but-unplayed response is never labelled delivered. The transcript preserves original STT wording even after a session-memory correction. This queue avoids database calls in the audio frame path; the existing raw JSONL flush still occurs there. On a database error, the browser receives an explicit saving warning, earlier committed rows remain, and a later server restart replays missing events from unchanged raw logs. Shutdown gives the writer 15 seconds and PDF jobs 30 seconds to flush after voice sessions close; unfinished raw events or PDF jobs recover on restart. This design assumes one local server process for the database and private files; concurrent replicas need coordinated recovery and storage.

A separate bounded PDF queue renders terminal records from persisted rows with ReportLab and an embedded Noto Sans font. PDFs go to `REHEARSE_PDF_DIR` (`private_pdfs/` by default), outside `/assets`, with owner-only file permissions and atomic replacement. A database claim prevents concurrent generation; interrupted `generating` jobs and missing files detected at startup regenerate from persisted rows. A failure leaves the transcript and outcome intact; only an admin can request CSRF-protected regeneration. Candidate detail and transcript APIs check ownership. Every PDF download and regeneration route checks the database-backed admin role before reading a file or starting work. Candidate APIs do not expose PDF status. Admin pages and APIs provide 20-record server-side pages with email/status filters. The PDF has a compact UTC metadata header, relative conversation times, status labels, and page numbers. It states that candidate text is machine transcription and server output does not confirm browser playback. A self-reported name appears only if supplied as persisted record metadata; current records do not store a separate name, so the account email identifies the candidate. The bundled font covers Latin, Greek, and Cyrillic examples; other scripts need additional embedded fonts and shaping validation. Local PostgreSQL, raw JSONL, and private PDFs need coordinated backups; no cloud storage or backup automation is provided.

Manual check: sign up two different candidates and sign in without email verification, start a short interview as each, then confirm each dashboard shows only its own record and partial status after disconnect. Candidate B must get 404 for candidate A's detail and transcript; both candidates must get 403 for every PDF route, including their own. Promote a third active account with the CLI, sign in, filter the admin list by each email, open both conversations, and download both PDFs after terminal states. Confirm the files render and that a prepared/cancelled assistant entry is identified as such. These checks do not establish microphone recognition or browser playback.

For the dedicated test database, first run:

```sh
DATABASE_URL=postgresql+asyncpg://rehearse:rehearse_local_only@127.0.0.1:5433/rehearse_test uv run alembic upgrade head
uv run pytest -q
```

The account integration tests use this test database and mocked email delivery; they never delete development data. A separate local end-to-end check used real SMTP capture in Mailpit. Mailpit is an inbox for development, **not production email delivery**. `/healthz` and the voice page's collapsed Diagnostics area show the running build ID. **End session** releases the microphone and peer connection immediately. Normal and spoken early closing use a short buffered-audio drain, which is not a browser playout acknowledgment.

## Candidate account architecture

`server.py` gates `/dashboard`, `/interview`, and `/api/offer` using the candidate obtained from the server session cookie. The browser never supplies a trusted candidate ID. `accounts.py` uses [FastAPI Users 15](https://fastapi-users.github.io/fastapi-users/latest/) for Argon2 password hashing, database-backed session strategy, and signed password-reset tokens. The package is in maintenance mode but receives security and dependency updates; its database strategy permits logout revocation and a 12-hour session lifetime. `accounts_db.py` defines PostgreSQL account, session, single-use link, rate-limit, interview, and transcript records; `migrations/` changes schema explicitly. Its existing `is_superuser` flag is the admin role; public sign-up ignores it, and only the local `rehearse_ai.admin` CLI promotes an existing active account. `Mailer` uses SMTP; local settings point to Mailpit. No database code enters the interview controller.

Password-reset links expire after one hour and are accepted once using a stored token digest. Legacy verification links can still be redeemed, but registration no longer sends one and verification is not required for access. Login and account actions have database-backed rate limits (login: 10 per email per 10 minutes; reset requests: 3 per email per hour, with IP limits too). The session cookie is HttpOnly and SameSite=Lax; production sets Secure. Unsafe account and WebRTC setup requests require a signed, one-hour CSRF token in both a cookie and request header. The login flow uses fixed internal destinations and ignores external return URLs. Token-bearing URLs are removed from browser history on page load; Uvicorn access logs are disabled so they are not recorded there. A future reverse proxy must also redact query strings. Email ownership is not verified. An unverified email address is not proof of personal identity.

For production configuration, use a private PostgreSQL `DATABASE_URL`, a new `REHEARSE_AUTH_SECRET`, `REHEARSE_ENV=production`, an HTTPS `REHEARSE_PUBLIC_BASE_URL`, and a real SMTP service through `REHEARSE_SMTP_HOST`, `REHEARSE_SMTP_PORT`, `REHEARSE_SMTP_FROM`, `REHEARSE_SMTP_USERNAME`, `REHEARSE_SMTP_PASSWORD`, and `REHEARSE_SMTP_STARTTLS=true`. Production email credentials and delivery have **not** been configured or tested. Local password-reset messages are captured at **http://127.0.0.1:8025/** by Mailpit, a development-only inbox; they are not delivered externally. Registration and login do not depend on SMTP. HTTPS termination, operational monitoring, scheduling, and backup/restore automation remain future work. Existing ignored JSONL voice logs and private PDFs are not exposed by static routes. Logging out or resetting the password stops that candidate’s active voice peer. A peer that remains connected across the 12-hour cookie expiry is not yet rechecked mid-call; new setup requests and HTTP routes require a live session.

## Architecture and provider choices

`SmallWebRTC` browser audio → Pipecat `VADProcessor` (Silero) → Deepgram streaming STT (`nova-3-general`) → Pipecat `UserTurnProcessor` → `InterviewInput` → OpenAI text LLM (`gpt-4.1-mini`, structured `run_inference`) → Cartesia streaming TTS (`sonic-3.6`, Skylar `db6b0ed5-d5d3-463d-ae85-518a07d3c2b4`) → `AudioObserver` → SmallWebRTC output → `DeliveryObserver`.

The STT, text LLM, and TTS are separate services; there is no realtime speech-to-speech model. The text LLM runs as a structured Pipecat service call outside the audio frame chain, and its validated JSON is never spoken directly. `interview.py` owns exact question order, state, limits, and the provider-independent `memory.py` session facts. `session.py` routes completed turns, validates decisions and literal fact extracts, cancels stale generations, and correlates utterance IDs. In `pipeline.py`, `InterviewInput` merges final STT chunks until turn completion; `AudioObserver` correlates TTS contexts and drops stale audio; `DeliveryObserver` observes transport speaking frames. `tts.py` chooses a provider and observes provider chunks independently of transport output. `session_log.py` writes raw ordered events. `interview_store.py` consumes those events through a bounded, ordered queue, and `transcript_pdf.py` renders from persisted rows. `config.py` validates provider credentials and account/email settings. Versioned prompt files in `src/rehearse_ai/prompts/` are the runtime authority; [PROMPTS.md](PROMPTS.md) includes their exact text and iteration record.

The candidate can introduce themselves by voice; no profile name or typed session-name confirmation is required. A name extracted from speech stays tentative. During the optional name question, an unclear reply gets one brief request to repeat or spell it; then the opening continues without a name. Explicit spoken spelling such as “My name is spelled N Y L A” confirms the spelling for this session. A clear spoken correction such as “It's Nyla, not Nila” supersedes the earlier interpretation and is acknowledged without spending a project probe. Later STT variants cannot silently overwrite a confirmed name. The session also remembers small project facts with source turn references; term corrections preserve the old value in correction history. Correction-only turns neither answer a question nor use its probe allowance; an ambiguous target gets one short clarification. The structured decision request includes current facts and asks for exact spans from the latest answer, which Python checks before storing as tentative. Raw STT is never rewritten. This memory stays in one session; it is not a durable profile or proof that a tentative extraction is accurate. The decision still uses one buffered model request, with a larger token cap for the optional fact list; latency impact has not been measured.

Deepgram offers streaming recognition but can mishear project names. The OpenAI text model supplies contextual proposals while Python enforces transitions; structured inference is fully buffered before TTS and can add delay. Cartesia uses Pipecat's streaming WebSocket service and was selected after a **six-request direct API diagnostic**: median request-to-first-PCM was **166.3 ms** for Cartesia and **1,277.8 ms** for OpenAI `gpt-4o-mini-tts`/`shimmer`; all six succeeded. These are three short utterances per provider, not reliability, voice-quality, browser, or end-to-end latency estimates. See [TTS_COMPARISON.md](TTS_COMPARISON.md) and its [tracked measurements](samples/tts-comparison-2026-10-26/measurements.json). Audio samples are local and ignored by Git. OpenAI TTS remains manually selectable through `REHEARSE_TTS_PROVIDER=openai`, with no automatic mid-response switch; its separate configuration and context-timeout diagnosis are in [TTS_DIAGNOSIS.md](TTS_DIAGNOSIS.md). Provider pricing, accents, and perceived voice quality were not benchmarked.

The configured Deepgram Nova-3 model supports optional [keyterm prompting](https://developers.deepgram.com/docs/keyterm), but hints are off for now. The candidate's name is generally unknown before they say it, and the installed Pipecat service reconnects its Deepgram stream when settings change. Introducing a hint after hearing a correction would risk disrupting live audio. Candidate terms emerge during the session; a hint is not confirmation that transcription is correct, and dynamic terms may appear in provider usage records. No provider or acoustic settings changed in this milestone.

## Turn-taking, interruptions, and evidence

Defaults are VAD confidence **0.7**, speech start **0.2 s**, VAD stop **0.35 s**, and one Pipecat `SpeechTimeoutUserTurnStopStrategy` with **1.1 s** speech timeout. The turn processor also has a **30 s failure watchdog**. The timeout was raised from **0.8 s** after a real follow-up answer split at “So the idea”; a separate orchestration fallback also advanced after a rejected extra probe. The 1.1 s value is a tuning starting point, not proven to cover every mid-answer pause. Final STT segments accumulate until Pipecat completes one user turn. Speech onset triggers Pipecat interruption and cancels pending LLM/TTS immediately, independently of the longer completion wait. Python keeps one substantive probe per main question, separates explicit repeat/skip/stop, and never treats an unheard generated question as delivered.

Agent text is prepared with an utterance ID before TTS, but enters the visible transcript only on server output start. A matching `BotStoppedSpeakingFrame` after TTS completion and without cancellation is the delivery acknowledgment; Pipecat can also emit stop on interruption, so stale and cancelled stops are ignored. A cancelled TTS context's late stop is filtered before transport output, and a fresh output start retires unmatched cancellation-stop accounting. This is **server output evidence**, not proof of browser playback or human hearing. Raw `sessions/<id>.jsonl` events use a common server monotonic session clock and retain final STT chunks, VAD stops, inference, provider audio, output, cancellation, and delivery. Final STT segments arriving before Pipecat's turn-start frame are tagged with the upcoming candidate turn at ingestion. The structured LLM call exposes no first-token timestamp and the browser supplies no reliable per-utterance playback onset. These remain null in the export; `tts_first_audio_ms` is explicitly labeled as a server-output proxy. Provider first-audio is a separate observation. Historical development sessions are not the future recording's evidence.

The author-confirmed [Loom recording](https://www.loom.com/share/928bba7d68ec4174856488a0ed2e1bb7) matches session `d564949d-6780-414f-8192-22bae9e9345d`. Its tracked [transcript](evidence/recorded-session/transcript.txt), [per-turn latency](evidence/recorded-session/latency.jsonl), and [measurement notes](evidence/recorded-session/latency_summary.md) come from that session. The recording reaches question four, includes requested provisional feedback, and ends at the candidate's spoken request; it does **not** demonstrate automatic final completion. A normal project answer starts around **0:46** in Loom's visible transcript. A mid-answer pause and an interruption while the agent speaks are not yet verified in the video; the exported rows do not mark an interrupted response. See [RECORDING.md](RECORDING.md) for scenario status.

For **12 of 14** candidate turns with a correlated server output start, estimated speech-end to output-start p50 is **2798.9 ms** and p95 is **5007.3 ms** (nearest rank); the mean is **3004.9 ms**. Available stage means are speech-end → last STT final **443.2 ms** (n=14), last STT final → turn completion **1008.6 ms** (n=14), and Cartesia request → first provider audio **102.9 ms** (n=12). These are observed intervals, not additive processing costs; two turns lack a correlated output. `user_stopped_ms` is estimated from Silero VAD stop minus its silence threshold. `tts_first_audio_ms` is explicitly a **server output start proxy**, while provider first audio is a separate field; browser playback onset and human hearing are unmeasured. The structured LLM call exposes no first-token timestamp, so `llm_first_token_ms` is null. Missing or ambiguous measurements remain null. The direct-provider medians above are a separate diagnostic, not end-to-end latency.

## Limits and next day

Session memory is limited to one current value per fact field. Text-model extraction may miss details even when the raw answer contains them; the prompt can still choose an unhelpful follow-up. Spoken correction parsing covers explicit “replacement, not earlier wording” forms and one target clarification, not arbitrary paraphrases. Letter-by-letter spelling depends on the STT service separating letters intelligibly; it does not prove the actual spelling. Acoustic confidence is unavailable, so a heard name remains tentative until the candidate explicitly spells or corrects it. The tracked recording and its latency figures predate this milestone and do not verify these new interactions.

The supplied video still needs scenario-level review for a natural pause and barge-in; the matching log ends through spoken early termination rather than normal final feedback. STT wording errors can still affect follow-ups; structured decisions may choose a poor detour or wait action despite Python guards. The single silence threshold trades fewer premature boundaries for slower turn endings. Browser playback onset, true human audibility, and LLM first token are unmeasured. With another day, I would add correlated browser playout telemetry, verify the recording's pause/interruption scenarios, tune turn timing from that evidence, and review more real answers for follow-up relevance before changing prompts.

**Prototype AI tools used:** Codex and ChatGPT assisted with implementation, debugging, testing, and documentation. **Prototype active time:** 4–5 hours across two days, as estimated by the author before the candidate-platform milestones. No revised time estimate has been provided for the newer work.

## Five-minute microphone check for session memory

Start with the command above. Give an unfamiliar name, such as one you actually use, and describe a GitHub pull-request project. Observe whether STT captures it correctly; this is separate from whether Python extracts it as a tentative name. If the name prompt mishears you, spell your name letter by letter aloud; verify the corrected spelling is remembered later. Pause mid-answer and continue, then correct a technical term aloud, for example “I said webhooks, not web books,” and add more answer content. Check that the same question remains active, the correction does not consume the one probe, and the next follow-up asks for a detail you have not already given. Interrupt a prepared reply once, then say “stop the interview.” Afterward, inspect the session's ignored `sessions/<id>.jsonl` for separate `stt_final_segment`, `candidate_final`, `correction_applied`, `memory_updated`, cancellation, and delivery events. Compare raw STT, name extraction, correction, and later name use separately. This is a manual acceptance script; the offline tests do not establish microphone recognition or audible behavior.
